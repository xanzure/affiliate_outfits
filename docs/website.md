# Vance Archives — Frontend Website

## Overview

Vance Archives is the public-facing frontend for the affiliate content engine. It is a minimalist fashion archive that displays concepts and their generated outfits, with interactive product flat-lays and affiliate shopping links.

The site is read-only. It does not write to the database, trigger pipeline runs, or handle authentication.

## Brand Direction

Quiet, editorial, restrained. Inspired by the brand feel of Acne Studios — understated confidence, generous whitespace, nothing decorative. The content is product flat-lays rather than model photography, so the design must carry the editorial weight through typography, spacing, and layout rather than imagery.

Color palette: warm off-white backgrounds, near-black text, no accent colors. Let the products speak.

## Pages

### `/` — Concepts Index

Displays all active concepts as a grid of cards.

Each card shows:

- Concept name (derived from `concept.seed`)
- Cover image (stored in `concept.metadata.cover_image_url`, falls back to a placeholder)
- Number of outfits generated

Clicking a card navigates to `/concept/:id`.

### `/concept/:id` — Concept Detail

Displays all outfits generated for a concept, in reverse chronological order.

Each outfit is shown as a numbered card (`#001`, `#002`, etc.) containing an interactive product flat-lay.

#### Outfit Flat-Lay

Products are rendered as individual images positioned on a canvas using absolute coordinates. Each product image is independently hoverable and clickable.

- **Hover**: subtle glow effect on the product image
- **Click**: opens a product panel showing name, retailer, price, and a link to the product page

Product layout (position, size, rotation) is stored per product in the outfit record. The backend also stores the rendered collage and its pixel manifest in the `collages` table for audit/history, but the frontend consumes `outfit.spec.layout` directly without inferring or auto-arranging.

## Data Models

The frontend consumes these shapes. They mirror the backend `models.py` types exactly.

### Concept

```ts
interface Concept {
  id: string
  seed: string
  status: "active" | "needs_review" | "retired"
  ranking_score: number
  last_posted_date_est: string | null
  created_at: string
  metadata: {
    cover_image_url?: string
    [key: string]: unknown
  }
}
```

### Product

```ts
interface Product {
  id: string
  retailer: string
  name: string
  category: string | null
  url: string
  affiliate_url: string | null
  image_url: string | null
  local_image_path: string | null
  price_cents: number | null
  currency: string
}
```

### ProductLayout

Stored inside `outfit.spec` per product. Generated by the collage layout layer.

```ts
interface ProductLayout {
  product_id: string
  x: number        // percent from left edge of canvas
  y: number        // percent from top edge of canvas
  width: number    // percent of canvas width
  rotation: number // degrees, can be negative
  z_index: number  // stacking order
}
```

### Outfit

```ts
interface Outfit {
  id: string
  concept_id: string | null
  concept_seed: string
  product_ids: string[]
  spec: {
    layout: ProductLayout[]
    [key: string]: unknown
  }
  created_at: string
  metadata: Record<string, unknown>
}
```

## Backend Integration

The frontend is currently built on local mock data. All mock data is typed to match the backend models exactly so that swapping in a real data source requires only replacing the data layer, not the UI.

### Current State (Mock)

- Concepts and outfits are defined in static TypeScript data files
- Product records are inlined into outfit mock data
- No API calls are made

### Future State (API)

The planned integration points are:

| Page | Endpoint | Notes |
|------|----------|-------|
| Concepts index | `GET /concepts` | Returns active concepts only |
| Concept detail | `GET /concepts/:id` | Returns concept + outfit list |
| Outfit products | `GET /outfits/:id/products` | Returns products with layout from spec |

These endpoints do not exist yet. When they are added to the backend, the frontend data layer (`src/lib/data.ts` or equivalent) should be the only file that changes.

### Product Links

Each product has a `url` (standard product page) and an `affiliate_url` (affiliate-tracked link, may be null). The frontend always prefers `affiliate_url` when present and falls back to `url`. This means affiliate integration requires no frontend changes — only the backend needs to populate `affiliate_url`.

### Collage Agent Output

The collage layout layer must write website-ready layout data into `outfit.spec.layout` as an array of `ProductLayout` objects. The frontend reads this array directly to position product images on the canvas. If `spec.layout` is absent or empty, the frontend falls back to a simple stacked default layout.

The backend stores full rendered-collage records in the `collages` table. `collages.layout_json` uses pixel coordinates and is for internal audit/history. `outfit.spec.layout` remains the frontend contract.

### Image Hosting

The website serves collage images as static assets from `web/public/images/collages/`. The pipeline saves the final rendered collage to that directory and records the public URL in `collages.collage_url` (e.g. `/images/collages/{outfit_id}.jpg`).

This `collage_url` is the single source of truth for the public-facing image. It is used for:

- TikTok and Pinterest autoposting — the publisher reads `collage.collage_url` to get the public URL required by platform APIs
- Concept cover images — when a collage is generated, the pipeline sets `concept.metadata.cover_image_url` to `collage.collage_url` so the concept card on the homepage shows a real image automatically

`Post.image_path` remains the local disk path used internally by the publisher. Individual product images are served directly from retailer CDNs via `product.image_url` and do not need to be hosted by the website.

## What The Frontend Does Not Handle

- Authentication or access control
- Publishing or scheduling
- Analytics ingestion
- Affiliate link generation
- Image scraping or processing
- Agent execution or pipeline triggering
- Payment or subscription logic
